1. Executive Summary

The “Car Parking NFC System” digitizes mall parking operations by combining Flutter clients, Firebase services, and NFC-enabled workflows. Customers self-book slots while admins can create manual check-ins and issue NFC cards that act as portable booking tokens. NFC tags store JSON payloads with booking identifiers, enabling rapid check-in/out and tamper-resistant auditing.

2. Technology Stack & Dependencies

  • Framework: Flutter 3.9.2 with Material 3 UI.
  • State Management: Riverpod 3 (providers for repositories, stats, booking data).
  • Backend: Firebase (Firestore, Auth, Storage).
  • NFC Plugin: nfc_manager 3.5.0 for Android/iOS tag access.
  • Build Targets: Android (minSdk per build.gradle.kts), iOS (requires iOS 13+ for NFCTagReaderSession).

3. High-Level Architecture

The app follows a layered approach:

  • Presentation Layer: Flutter screens split into customer and admin packages. Example: ManualBookingScreen, AdminDashboardScreen, BookingConfirmationScreen.
  • State Layer: Riverpod providers live under lib/data/providers, exposing booking lists, statistics, and slot info.
  • Domain/Data Layer: Firestore-backed repositories (lib/data/repositories) manage models such as GlobalBookingModel.
  • Core Services: Shared utilities under lib/core, notably nfc_service.dart for tag IO.

4. Data Layer & Firestore Collections

Main collections:

  • bookings: Documents shaped by GlobalBookingModel containing status, slot, user, timestamps, encrypted payload, etc.
  • malls: Mall metadata (total slots, available slots, zones) that powers dashboards and slot selection.
  • parkingSlots: Individual slot state (occupied/reserved/available) used by manual booking and dashboards.
  • users: Authentication and profile data when tied into Firebase Auth.

Repositories interact with Firestore, transforming snapshots into models and vice versa. Example: bookingRepositoryProvider handles creation, lookups, and status updates.

5. Core Modules & Key Files

5.1 Presentation Screens

  • ManualBookingScreen (lib/presentation/screens/admin/manual_booking_screen.dart): Admin UI for manual entries, now delegating NFC writing to a separate screen.
  • ManualBookingNfcScreen (.../manual_booking_nfc_screen.dart): Dedicated NFC writer with progress, retry, and result propagation.
  • AdminDashboardScreen: Central hub for statistics, slot overview, NFC-based checkout scanning, and quick actions.
  • User-facing screens: SlotSelectionScreen, VehicleDetailsScreen, BookingConfirmationScreen deliver the customer journey.
  • WriteNfcScreen: Developer/QA sandbox for raw tag operations.

5.2 Services & Utilities

  • NFCService (lib/core/services/nfc_service.dart): Thread-safe wrapper over NfcManager for read/write/clear operations with JSON payloads.
  • Providers: Riverpod definitions (e.g., activeBookingsForMallProvider) delivering reactive data to widgets.

5.3 Routing

lib/routes.dart centralizes admin route constants. lib/main.dart registers MaterialApp routes, validating arguments and providing fallback UI when arguments are missing.

6. Primary User Flows

6.1 Customer Web/App Booking

  1. Select mall/slot via SlotSelectionScreen.
  2. Enter vehicle + driver details.
  3. Confirm booking → Firestore booking created → BookingConfirmationScreen shows QR/NFC instructions.

6.2 Admin Manual Booking & NFC Issuance

  1. Open ManualBookingScreen, fill vehicle + driver info, pick slot.
  2. App creates GlobalBookingModel entry.
  3. Navigates to ManualBookingNfcScreen with booking payload.
  4. Admin taps “Write to Tag,” holds NFC card, sees success/failure, and returns.
  5. Dashboard stats/providers invalidated to reflect occupancy change.

6.3 NFC Checkout on Dashboard

  1. Admin taps “Scan NFC for Checkout.”
  2. NFCService reads tag → bookingId retrieved.
  3. App fetches booking, launches checkout screen, and after completion clears NFC tag.

7. NFC Implementation Details

  • Payload: JSON encoded booking data, stored as MIME application/json NDEF records.
  • Session gating: _sessionActive in NFCService prevents concurrent sessions and ensures stopSession() resets state.
  • Error handling: Failures propagate via exceptions and UI snack bars. ManualBookingNfcScreen offers retry/cancel UI.
  • Sandbox: WriteNfcScreen demonstrates minimal usage for troubleshooting hardware.

8. Android Platform Configuration

  • Manifest: Declares <uses-permission android:name="android.permission.NFC"/> and marks android.hardware.nfc as required.
  • Intent Filters: TAG_DISCOVERED, NDEF_DISCOVERED, TECH_DISCOVERED (priority 999) route scanned tags to the Flutter activity when needed.
  • Tech list: android/app/src/main/res/xml/nfc_tech_filter.xml enumerates supported tag technologies.
  • Activity lifecycle: Launch mode is singleTask to avoid duplicate Flutter activity instances.

9. Build, Deployment & Environment Setup

  • Flutter Commands: flutter clean && flutter pub get, flutter run --release.
  • Firebase: Initialize with platform-specific FirebaseOptions in main.dart. Ensure Google Services JSON/Plist are configured.
  • Testing NFC: Requires physical Android device or iOS hardware with NFC. Emulators without NFC will skip writing but still create bookings.
  • PDF Documentation: Convert this HTML via pandoc docs/manual_nfc_documentation.html -o project_documentation.pdf or browser “Print to PDF.”

10. Advantages & Future Enhancements

Advantages

  • Operational Clarity: Separate admin/customer flows keep UX focused.
  • Reliability: Shared NFCService + Riverpod providers reduce duplicated logic.
  • Extensibility: New NFC scenarios (season passes, loyalty) can reuse ManualBookingNfcScreen.
  • Observability: Firestore data + dashboards provide real-time slot visibility.

Future Enhancements

  • Automated PDF receipts after NFC checkout.
  • Offline caching for manual bookings when network is unstable.
  • Role-based access control to limit who can issue tags.
  • Telemetry on NFC failures to monitor hardware issues.
